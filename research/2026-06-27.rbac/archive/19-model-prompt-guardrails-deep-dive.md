# Model/prompt guardrails deep dive

This page breaks down the model- and prompt-level guardrail tools listed in [16-existing-out-of-process-proxies.md](./16-existing-out-of-process-proxies.md). They are all useful **additional** layers, but none of them can replace a tool-call proxy or OS-level isolation for Hermes.

---

## Why model/prompt guardrails are not enough for Hermes

Hermes' highest-risk operations happen **after** the LLM has decided to call a tool:

- `terminal("rm -rf /")`
- `execute_code` running arbitrary Python
- `send_message` exfiltrating data
- `read_file` on `~/.ssh/id_rsa`
- MCP tools invoked with attacker-controlled arguments

Guardrails that inspect prompts, outputs, or reasoning traces can reduce the *probability* that the LLM chooses a dangerous action, but they do not remove the *capability* to perform that action. A compromised or misaligned model, a poisoned tool description, or a malicious skill can still reach the tool execution layer.

Therefore these tools belong in a **defense-in-depth** stack, not as the primary enforcement boundary.

---

## 1. LlamaFirewall (Meta)

**What it is.** An open-source guardrail framework from Meta's Purple Llama project. It combines three scanners:

- **PromptGuard 2** — fine-tuned BERT-style classifier that detects adversarial prompts and direct prompt injection in user prompts and untrusted inputs.
- **Agent Alignment Checks** — chain-of-thought auditor that inspects the agent's reasoning trace for goal hijacking and indirect prompt injection.
- **CodeShield** — online static analysis engine (Semgrep + regex rules) for insecure code generated by coding agents.

**What it protects against.** Adversarial prompts, indirect prompt injection, agent goal misalignment, and insecure code generation.

**How it works.** Inputs are run through PromptGuard 2 before entering the agent context. As the agent reasons, AlignmentCheck compares the execution trace to the original user objective. Generated code is passed through CodeShield before execution.

**Why it is not enough alone.**

- It scores/audits; it does not enforce at the host execution boundary.
- A prompt-injection payload that bypasses PromptGuard 2 can still produce a malicious tool call.
- It runs **inside** the agent application or as a library, so a compromised agent process can disable or bypass it.
- Hermes' native tools (`terminal`, `execute_code`) are outside LlamaFirewall's scope.

**When to use it.** As an input-filtering and reasoning-audit layer on top of a tool-call proxy. Good for catching prompt-injection attempts early.

## 2. NeMo Guardrails (NVIDIA)

**What it is.** An open-source Python toolkit (Apache 2.0) for adding programmable rails to LLM-based conversational systems. It uses a domain language called **Colang** to define dialog flows and safety policies.

**What it protects against.** Off-topic conversations, unwanted topics, adversarial prompts, hallucinations, unsafe retrieval chunks, and unwanted execution paths.

**How it works.** Every turn passes through five rail stages:

1. **Input rails** — filter or mask user input.
2. **Dialog rails** — keep the conversation on a defined path using Colang flows.
3. **Retrieval rails** — reject or redact RAG chunks.
4. **Execution rails** — gate tool/action execution.
5. **Output rails** — validate the model's response.

**Why it is not enough alone.**

- Conversation-level, not per-tool argument enforcement.
- The rails are defined in the same process space as the agent; a compromised agent can alter the Colang config or skip the rail runtime.
- It does not provide an out-of-process audit log that the agent cannot tamper with.
- Hermes' native tool registry is not governed by NeMo Guardrails.

**When to use it.** To keep an LLM assistant on-topic and to add input/output filters. Not as the sole boundary for tool execution.

---

## 3. Guardrails AI

**What it is.** An open-source Python framework for validating LLM inputs and outputs using composable validators from Guardrails Hub. It supports schema validation, PII detection, toxicity checks, hallucination detection, and more.

**What it protects against.** Malformed outputs, PII leakage, toxic content, adversarial prompts, and schema violations.

**How it works.** Developers define a `Guard` that wraps an LLM call. The guard applies validators; if validation fails it can raise an exception, re-prompt, or fix the output.

**Why it is not enough alone.**

- Output schemas and content filters are not tool authorization.
- It validates *what the model returns*, not *what the agent does* with a tool.
- Like NeMo Guardrails, it typically runs inside the agent process and can be bypassed if that process is compromised.
- It has no native understanding of Hermes tools or MCP tool names.

**When to use it.** For structured-output reliability and output hygiene. Useful as a post-processing filter, not as the primary security boundary.

---

## 4. Galileo Agent Control

**What it is.** An open-source agent control plane (Apache 2.0) launched by Galileo in March 2026. It lets organizations define centralized policies and enforce them across agents through a `@control()` decorator.

**What it protects against.** Unwanted agent behavior, policy violations, unsafe outputs, and fleet-wide governance gaps.

**How it works.** Agents register with a central policy server. Each agent/tool call is evaluated against pluggable evaluators (Galileo Luna, AWS Bedrock, NVIDIA NeMo, Cisco AI Defense, custom evaluators). Policies can be updated centrally without redeploying agents.

**Why it is not enough alone.**

- Framework-level governance; not a transparent MCP proxy.
- Requires agent code to be instrumented with the `@control()` decorator or SDK.
- Hermes would need a native integration or source-code changes; it cannot be dropped in transparently.
- A compromised Hermes process could bypass the decorator for native tools.

**When to use it.** For enterprises running multiple agent frameworks that need a single governance layer. Less suitable for hardening a single black-box agent like Hermes without code changes.

---

## 5. AI EdgeLabs / Parallax

**What it is.** AI EdgeLabs is a runtime security platform; **Parallax** is its open-source Rust evaluator engine. Parallax intercepts agent messages and tool calls at four lifecycle stages and runs them through a cost-ordered chain of evaluators (regex, keyword, Sigma rules, CEL, SQL temporal analysis).

**What it protects against.** Prompt injection, secret leakage, PII exposure, data exfiltration, dangerous commands, privilege escalation, and behavioral anomalies.

**How it works.** It can run as an HTTP `/evaluate` endpoint or as a transparent proxy. Each tool call is classified, inspected, and logged; verdicts are `allow`, `redact`, or `block`.

**Why it is not enough alone.**

- More network/host oriented than MCP tool semantic; it sees bytes, not the structured intent of a tool call.
- It does not understand Hermes' native tool registry or MCP tool naming.
- Policy is still evaluator-chain based; complex argument-level policies require custom rules.
- The transparent proxy mode is promising, but adoption and community are smaller than ContextForge/Envoy.

**When to use it.** As a runtime evaluator alongside an MCP proxy, especially for DLP and behavioral drift detection.

---

## 6. CrabTrap (Brex)

**What it is.** An open-source HTTP/HTTPS proxy from Brex that uses LLM-as-a-judge to decide whether each outbound request from an AI agent matches an allowed-traffic policy.

**What it protects against.** Unauthorized outbound HTTP calls, data exfiltration, SSRF, and misuse of external APIs.

**How it works.** Set `HTTP_PROXY`/`HTTPS_PROXY` to CrabTrap. It intercepts all outbound requests, evaluates them against deterministic rules and an LLM judge, and forwards or blocks them. It performs TLS interception for HTTPS.

**Why it is not enough alone.**

- HTTP-layer judgment, not MCP tool-level policy. It does not understand that `mcp_github_create_issue` and `mcp_github_delete_repo` are different risks.
- LLM-as-a-judge is probabilistic; judges can be gamed or hallucinate.
- It only sees network traffic, so native Hermes tools that never leave the process (`terminal`, `execute_code`, `read_file`) are invisible to it.
- Requires trusting the proxy CA in the agent container.

**When to use it.** As a complementary egress control for HTTP-based tools and external API calls, especially in combination with Pipelock or ContextForge.

---

## 7. AIRG (runtime governance library)

**What it is.** A small, MIT-licensed Python library described as a runtime governance library that intercepts AI agent tool calls before execution using YAML-defined contracts.

**What it protects against.** Specific dangerous tool-call patterns (e.g., `curl` with a token, `rm -rf`, secret leakage in output).

**How it works.** Contracts define `pre` and `post` rules on tool names and arguments. The library wraps tool execution and applies allow/deny/redact actions.

**Why it is not enough alone.**

- Still a plugin/library pattern; it runs in the same process as the agent.
- A compromised agent can monkey-patch the wrapper or call tools directly.
- Tiny project with minimal adoption and no out-of-process audit guarantee.
- Does not cover native Hermes tools unless each one is manually wrapped.

**When to use it.** As a lightweight in-process filter during prototyping, not as a hardening boundary.

---

## 8. McpVanguard / VEX

**What it is.** An early-stage MCP security gateway from ProvnAI. **McpVanguard** is a transparent MCP interception proxy; **VEX** is a cryptographic pre-inference gate and Merkle-linked audit trail.

**What it protects against.** Malicious MCP tool calls, poisoned tool descriptions, rug-pull MCP server updates, and tampered audit logs.

**How it works.** McpVanguard sits between the MCP client and server, inspects tool descriptions and tool-call arguments, and enforces a default-deny capability policy. VEX adds cryptographic attestation of intent and an append-only, hash-chained audit log.

**Why it is not enough alone.**

- Early; small user base and unproven at scale.
- Only protects MCP-mediated calls. Native Hermes tools bypass it entirely.
- The VEX cryptographic chain is a strong audit idea, but the project is not yet a mature, widely-trusted foundation.

**When to use it.** Watch it closely. If it matures, it could become a strong MCP-specific enforcement layer, but today it should not be the sole foundation.

## Summary: where each guardrail fits

| Tool                       | What it guards                            | What it cannot guard                     | Recommended role                     |
|----------------------------|-------------------------------------------|------------------------------------------|--------------------------------------|
| **LlamaFirewall**          | Prompts, reasoning traces, generated code | Native tool execution                    | Input/reasoning audit layer          |
| **NeMo Guardrails**        | Conversation flow, topics, input/output   | Per-tool argument policy                 | Conversational safety layer          |
| **Guardrails AI**          | Output schemas, PII, toxicity             | Tool authorization                       | Output validation layer              |
| **Galileo Agent Control**  | Fleet-wide agent policies                 | Transparent MCP/native tool interception | Central governance for custom agents |
| **AI EdgeLabs / Parallax** | Runtime messages/tool-call bytes          | Semantic MCP tool policy, native tools   | Runtime DLP/behavioral layer         |
| **CrabTrap**               | Outbound HTTP requests                    | Native tools, MCP semantics              | Egress/judge layer for HTTP tools    |
| **AIRG**                   | In-process tool-call patterns             | Native tools, process compromise         | Lightweight prototype filter         |
| **McpVanguard / VEX**      | MCP tool calls and audit integrity        | Native Hermes tools                      | Experimental MCP enforcement         |

---

## Bottom line for Hermes

Use model/prompt guardrails to **reduce the chance** that a dangerous tool call is ever generated. Use ContextForge (or another MCP proxy) plus disabled native tools and OS-level isolation to **make dangerous actions impossible** even when the guardrails fail.

The correct mental model is:

```
Guardrails → LLM → MCP proxy/native-tool policy → OS sandbox → host
```

Guardrails sit at the left of that chain. They are not the right end of it.
